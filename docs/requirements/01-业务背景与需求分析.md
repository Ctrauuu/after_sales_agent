# 01 · 业务背景与需求分析

> 这篇文档讲的是"为什么要做这个项目"。如果你是新人接手，读完能搞清楚苏宁售后团队现在的痛点是什么、这个 Agent 要解决什么问题、上线后怎么衡量效果。

---

## 一、业务背景

苏宁易购是国内少数具备"线上电商 + 线下门店 + 自有物流 + 自有售后服务体系"全链条能力的零售企业。其售后业务每天处理大量退换货、维修、清洗、安装工单，覆盖家电、3C、超市、母婴等几十个品类。

目前售后团队做数据分析和运营监控的典型流程是：

1.  登录多个后台系统（订单系统、工单系统、BI 看板）
    
2.  手动筛选条件导出 Excel
    
3.  人肉做数据透视和分析
    
4.  写周报/月报汇总
    

一个"最近退单最多的品类是什么"这样的问题，运营可能要先找 BI 团队提需求，半天后才能拿到结果。如果中途想换个维度追问——比如"空调退单的原因分布"——又得重新走一遍流程。这种"数据找人"而不是"人问数据"的模式，在售后这种对时效极其敏感的业务里，已经是明显的效率瓶颈。

更深层的问题在于：**售后数据散落在多个独立系统中**。一个订单从"用户申请退货→审核→上门取件→仓库签收→质检→退款"这六七个节点，每个节点的状态存在不同的数据库里。想串起来看一个订单的完整链路，得跨三四个系统来回翻。一线客服主管处理投诉升级时，往往要同时打开订单后台、工单后台、物流后台、支付后台，才能拼出一个完整的时间线。

## 二、使用场景

以下是五个有画面感的真实使用场景。

### 场景1 · 售后运营晨会问数

售后运营经理张哥，早上9点开晨会前在飞书群里 @机器人：

> "昨天全渠道退单量多少，环比涨了还是跌了？"

Agent 30秒内回复："昨天退单总量1,283单，环比前日+5.2%，较上周同日+3.8%。"

张哥追问："哪个品类涨得最狠？"

Agent 下钻："空调品类328单，环比+23%，是涨幅最大的品类。"

再追问："空调退单原因集中在哪几个？"

Agent 调取退单原因字段聚合："安装问题42%（137单）、产品质量问题31%（102单）、七天无理由退货27%（89单）。其中'安装后异响'子类目占安装问题中的68%，集中在某品牌1.5匹变频挂机型号。"

从发现异常到定位根因，三句话完成。全程不需要打开任何后台。

### 场景2 · 客服主管处理投诉升级

VIP用户王女士电话投诉"我买的洗衣机申请退货一周了还没退款，你们到底处理到哪步了"。

客服主管李姐在钉钉上 @机器人：

> "查订单 S2024060100123 的售后全链路"

Agent 跨四个系统拉出一条时间线：

```plaintext
━━ 订单 S2024060100123 售后全链路 ━━

6月1日 14:23  用户提交退货申请（原因：运行噪音大）
6月2日 09:15  客服审核通过，生成工单 R2024060200456
6月3日 10:30  物流上门取件完成（师傅：刘建国，运单号 SF12345678）
6月5日 08:40  南京江宁仓签收入库
6月5日 08:40  → 质检状态：待检测（已滞留2天）

⏱ 总处理时长：已超SLA（72小时），当前卡点：仓库质检
```

李姐一眼定位到卡在仓库质检环节，直接给仓库打电话催单。从接到投诉到找到根因，前后不到两分钟。

### 场景3 · 品控工程师做质量分析

品控工程师小王在企微群里问：

> "近30天退单率超过5%的 SKU 有哪些？把退单原因分布也拉出来"

Agent 列出问题 SKU 清单。小王继续追问：

> "退单率最高的那个型号，近90天的退单趋势图拉一下，顺带看看是不是有集中投诉的批次号"

Agent 生成趋势图，标记了三个异常波峰，对应的批次号分别是 B20240501、B20240515、B20240602。小王把数据和截图发给供应商，启动质量回溯。

### 场景4 · 区域经理盯售后时效

华东大区经理老陈在飞书问：

> "我负责的江浙沪区域，近7天维修工单的 SLA 达成率是多少？没达成的集中在哪些城市？"

Agent 按区域权限自动限定数据范围后回复："江浙沪区域近7天维修工单 SLA 达标率 87.3%。未达标工单集中在南京（43单，达标率79%）、杭州（28单，达标率82%）。主要原因是配件缺货导致等待超时。"

老陈追问："南京那43单未达标的，具体是哪些配件缺货"，Agent 列出 Top3 缺货配件及对应工单数，老陈直接截图发南京城市经理群里督办。

### 场景5 · 高层月度复盘

集团 VP 在每个月的复盘会上，直接在飞书群 @机器人：

> "本月售后核心指标简报：退单率、退单金额、平均处理时效、用户满意度，跟去年同期对比"

Agent 生成结构化报告：

```plaintext
━━ 2026年5月售后核心指标 ━━

退单总量：38,492单（同比+2.1%）
退单率：3.2%（同比+0.3pp）
退单金额：约1,280万元（同比+1.8%）
平均处理时效：47.3小时（同比+5.2小时，恶化）
用户满意度：4.2/5（同比-0.1）

⚠ 预警：平均处理时效连续3个月上升，建议重点关注仓库质检环节瓶颈。
```

## 三、解决的核心需求

| 需求维度 | 现状 | 目标 |
| --- | --- | --- |
| 数据查询时效 | 提需求→半天出数，依赖BI团队 | 自然语言即问即答，30秒内出结果 |
| 异常发现速度 | 依赖周报/月报，滞后3~7天 | 每日自主追问，当天发现当天响应 |
| 单订单全链路查询 | 跨3~4个系统手动翻查，10分钟以上 | 一句话拉出完整时间线，10秒内 |
| 多维数据交叉分析 | 导出Excel后人工透视 | 对话式逐层下钻，追问即分析 |
| 团队协同效率 | 数据散落各自本地，信息不对称 | 群聊共享查询结果，所有人看到同一份数据 |
| BI团队人力释放 | 大量临时取数需求占用人天 | 日常查询自助化，BI聚焦深度分析 |

## 四、业务边界

明确几条"不做"的线，防止范围蔓延：

1.  **不面向C端消费者**。这是内部运营工具，不发退货流程、不跟用户聊天、不替代苏宁现有客服系统。
    
2.  **不写入业务数据**。所有 MCP 调用均为只读查询，Agent 不会修改订单状态、不会操作退款、不会创建工单。
    
3.  **不替代 BI 系统**。复杂报表、大屏可视化、离线数据分析仍走 BI 平台。Agent 做的是"即时问答"，不是"数据仓库"。
    
4.  **不支持自然语言建表/ETL**。NL2SQL 仅限于 SELECT 查询，不涉及 DDL/DML。
