# 09f · 飞书上下文槽位部署与测试案例集

本文用于验收 `suning-rbac-bridge` 插件中的 `pre_llm_call` / `post_llm_call` Hooks。测试重点是：
`topic/new_filters` 由 LLM 结构化提取，增量值经过数据库白名单，置信度不足时不污染槽位，并且后续回答
确实继承已确认上下文。长期记忆 FTS5 异步写入不在本轮验收范围内。

## 一、部署准备

### 1. 安装 Python 3.11+ 公共包

后端 `uv sync` 会通过 editable source 自动安装公共包；Hermes 使用自己的 Python 3.11 虚拟环境，需单独执行：

```bash
uv pip install \
  --python /home/ctrau/.hermes/hermes-agent/venv/bin/python \
  --editable /home/ctrau/suning-hermes-agent/packages/suning-context-runtime
```

验证依赖：

```bash
/home/ctrau/.hermes/hermes-agent/venv/bin/python -c \
  "import langchain, langchain_deepseek, suning_context_runtime; print('context runtime ok')"
```

### 2. 配置 Hermes 进程环境

在 `~/.hermes/.env` 中填写以下变量。它们必须是 Hermes Gateway 进程可见的配置，只有
`backend/.env` 中存在还不够。

```dotenv
REDIS_URL=redis://127.0.0.1:6380/0
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=suning_readonly
MYSQL_PASSWORD=<只读账号密码>
MYSQL_DATABASE=suning_aftersale

DEEPSEEK_API_KEY=<DeepSeek 密钥>
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash

CONTEXT_LLM_TIMEOUT_SECONDS=15
CONTEXT_SLOT_CONFIDENCE_THRESHOLD=0.7
CONTEXT_WHITELIST_TTL_SECONDS=300
```

MySQL 账号只需要查询业务候选值的 `SELECT` 权限；不要给 Hooks 使用建表或写数据账号。

### 3. 启动依赖并重启 Gateway

```bash
cd /home/ctrau/suning-hermes-agent/backend/infra/mysql
docker compose --env-file .env up -d

hermes gateway restart
hermes gateway status
tail -f ~/.hermes/logs/gateway.log
```

启动日志中不应出现“结构化上下文 Hooks 配置不完整”。若数据库暂时不可用，插件保留既有 RBAC
工具；本轮新槽位不写入，回答链路仍可继续。

### 4. 灰盒检查方法

飞书侧只检查回答是否继承条件；需要核对内部状态时，先找到最近的 `conv:*` 键，再查看 JSON：

```bash
redis-cli -u redis://127.0.0.1:6380/0 --scan --pattern 'conv:*'
redis-cli -u redis://127.0.0.1:6380/0 GET 'conv:<session_id>'
```

重点字段是 `user_id`、`slots.topic`、`slots.filters`、`slot_confidence`、`turn_count` 和
`recent_turns`。`last_reply_summary` 只用于理解指代，不得出现在业务工具参数中。

## 二、飞书端测试案例

除特别说明外，每个案例使用新的飞书私聊会话，且同一案例中的消息必须按顺序发送。数据结果受当前
数据库和用户 RBAC 范围影响，因此验收槽位条件和回答口径，不硬编码统计数字。

### FS-CTX-01：连续追问继承

| 轮次 | 飞书输入 | 预期槽位 | 预期回答行为 |
| --- | --- | --- | --- |
| 1 | `查最近30天空调退单情况` | `topic=return_analysis`；`category=空调`；`date_range_days=30` | 查询当前用户权限内最近 30 天空调退单 |
| 2 | `按原因拆一下` | 继承前两项；新增 `group_by=reason` | 仍是最近 30 天空调，不要求用户重述条件 |
| 3 | `再按品牌看` | 继承品类和时间；`group_by` 覆盖为 `brand` | 回答品牌维度，不继续沿用原因维度 |

通过标准：Redis 中不存在重复槽位；同名 `group_by` 被新值覆盖，没有任何槽位删除操作。

### FS-CTX-02：本轮显式值覆盖

| 轮次 | 飞书输入 | 预期槽位 |
| --- | --- | --- |
| 1 | `看最近7天冰箱退单` | `category=冰箱`；`date_range_days=7` |
| 2 | `改看30天` | `category=冰箱` 保持；`date_range_days=30` |
| 3 | `品类换成空调` | `category=空调`；`date_range_days=30` 保持 |

通过标准：只覆盖用户本轮明确修改的字段，其余条件继续继承。

### FS-CTX-03：确认的话题切换

| 轮次 | 飞书输入 | 预期槽位 |
| --- | --- | --- |
| 1 | `查最近30天空调退单，按原因分组` | `topic=return_analysis`，保存统计条件 |
| 2 | `查订单202406010001详情` | `topic=order_query`；`order_id=202406010001`；不继承退单的 `group_by` |
| 3 | `再看订单202406010003` | 保持 `order_query`；`order_id` 覆盖为新值 |

通过标准：切换话题时旧业务条件不跨主题泄漏；这属于话题边界重建，不是面向用户的槽位删除能力。

### FS-CTX-04：退单编号跨工具复用

| 轮次 | 飞书输入 | 预期行为 |
| --- | --- | --- |
| 1 | `查退单1的处理流程` | `topic=return_case`；`return_id=1`；调用售后流程工具 |
| 2 | `物流到哪了` | 继承 `return_id=1`；调用物流工具 |
| 3 | `退款状态呢` | 继续继承 `return_id=1`；调用退款工具 |

通过标准：第二、三轮不要求再次输入退单号，且 `return_id` 没有被误放到退单统计话题。

### FS-CTX-05：商品 SKU 名称与编码白名单

| 轮次 | 飞书输入 | 预期槽位与行为 |
| --- | --- | --- |
| 1 | `查商品 SKU-AC-GL-15P` | `topic=product_query`；`sku_code=SKU-AC-GL-15P` |
| 2 | `这个商品是什么品牌和品类` | 继承 SKU，回答格力及对应空调品类 |

通过标准：SKU 必须存在于 `t_product_sku`；大小写或商品名别名最终规范化成数据库 SKU 编码。

### FS-CTX-06：数据库值域规范化

发送：`看华东区域最近30天美的空调退单，按原因分析`。

预期：

- `region` 规范化为数据库编码 `HD`；
- `brand` 规范化为数据库品牌名 `美的`；
- `category=空调`、`date_range_days=30`、`group_by=reason`；
- 回答仍受 MCP 服务端当前用户 RBAC 限制，槽位白名单不能扩大权限。

### FS-CTX-07：不存在的数据库候选值

发送：`统计最近30天火箭品类的退单，按品牌看`。

预期：`火箭` 不在 `t_product_category`，不得写入持久化 `category` 槽位；Gateway 不应因白名单
失败而崩溃。Agent 可以要求用户改用品类白名单中的名称，或明确返回没有可确认的品类，不能把“火箭”
保存后影响下一轮。

### FS-CTX-08：模糊追问与低置信度

| 轮次 | 飞书输入 | 预期行为 |
| --- | --- | --- |
| 1 | `看最近30天空调退单` | 建立明确的退单统计上下文 |
| 2 | `那个再看看` | 当提取置信度低于 0.7 时，不新增、不覆盖任何槽位；保留原话题 |

通过标准：`slot_confidence < 0.7` 时 `slots.filters` 与上一轮一致。Agent 可基于已有上下文回答或追问，
但不能凭空增加品牌、区域、状态等条件。

### FS-CTX-09：话题字段白名单

发送：`分析最近30天空调退单，订单号是202406010001`。

预期：若模型判断为 `return_analysis`，统计字段可以保留，但 `order_id` 不在该话题允许字段中，不能写入
该话题槽位。若用户真正要查订单，Agent 应确认意图或将整个话题识别为 `order_query`，不能混合两套条件。

### FS-CTX-10：同一会话用户隔离

准备两个已授权飞书账号 A、B。分别私聊机器人建立不同上下文：A 查询空调，B 查询冰箱；随后双方都发送
`按原因看`。

预期：A 只继承空调，B 只继承冰箱。灰盒检查中每个 `session_id` 的 `user_id` 与飞书可信发送者一致；
即便发生异常 session 复用，只要发送者变化也会重建空上下文，禁止继承上一用户条件。

### FS-CTX-11：超过十轮的历史压缩

在同一会话围绕空调退单连续发送 11 轮有效追问。第 11 轮完成后检查 Redis：

- `turn_count=11`；
- `recent_turns` 只保留最近 3 轮；
- `compressed_history` 新增一条不超过 400 个汉字的摘要；
- 摘要保留用户目标、有效条件、关键结论和修正，不出现模型虚构事实。

### FS-CTX-12：依赖故障降级

测试环境短暂停止 MySQL，保留 Redis 和 Gateway，然后在已有会话中发送 `按原因拆一下`。

预期：日志记录白名单读取失败，本轮不写入未经校验的新槽位；已有槽位仍可作为回答参考，Gateway 和 RBAC
工具注册不应消失。恢复 MySQL 后，白名单缓存重新加载即可继续提取。
